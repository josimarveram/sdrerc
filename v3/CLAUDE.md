# CLAUDE.md (v3) - Contexto operativo para Claude Code en SDRERC V3

Este archivo resume el contexto vigente de **SDRERC V3** (la migración web de SDRERC V2), scoped a este directorio `v3/`. Claude Code lo carga automáticamente al trabajar dentro de `v3/`, además del `CLAUDE.md` raíz (que sigue siendo la fuente para V2 y las restricciones que aplican a todo el repo, como no tocar V2 ni ejecutar SQL sin autorización).

Relación con otros documentos:

- `../CLAUDE.md` (raíz): contexto operativo de V2. Prevalece para todo lo que sea V2, y sus restricciones permanentes (no tocar legacy, no SQL sin autorización, no secretos en el repo, reglas de git) aplican igual aquí.
- `../docs/arquitectura_app/PLAN_MIGRACION_SDRERC_V3.md` (+ `.docx`): el plan/roadmap — stack, fases, diseño, criterio de "módulo validado". Sigue siendo la referencia para *qué sigue* y *por qué en ese orden*.
- Este archivo (`v3/CLAUDE.md`): el registro operativo de *cómo quedó construido* cada pieza de V3, los patrones ya establecidos y qué quedó deliberadamente fuera de alcance en cada incremento. Se actualiza cada vez que se cierra un incremento de fase.

**Regla permanente (pedido explícito del usuario, 12/08/2026): todo cambio en `v3/` — código, config, infraestructura de desarrollo, decisiones de alcance — se refleja en este archivo antes de dar la tarea por terminada.** No solo al cerrar una fase completa: un incremento parcial, un fix de entorno, un patrón nuevo establecido o un alcance diferido también califican. Si algo cambia y este archivo no se actualiza, se considera trabajo incompleto.

## Regla de inicio para Claude Code (en v3/)

1. Leer `../CLAUDE.md` (V2) y `../docs/arquitectura_app/PLAN_MIGRACION_SDRERC_V3.md`.
2. Leer este archivo.
3. **Antes de portar cualquier pantalla nueva**: leer el panel Swing real de V2 (`JPanelXxxV2.java`) para confirmar campos/columnas exactos. Ver "Principio rector" abajo — regla mandatoria, no opcional.
4. Revisar los archivos reales ya portados en `v3/` que toquen el mismo módulo antes de asumir su forma.
5. Al terminar la tarea: actualizar este archivo con lo que cambió (ver regla permanente arriba).

## Principio rector: paridad de datos/campos, libertad de diseño

V3 debe coincidir con V2 en **campos, columnas y agrupamiento de secciones** (verificado contra el código Swing real), pero tiene libertad total de diseño visual/responsive — no es un clon pixel a pixel.

Esta regla se volvió mandatoria (no solo recomendada) después de dos correcciones explícitas del usuario en la Fase 2:

1. El primer borrador del formulario "Registro manual" inventó un agrupamiento de campos propio (agregó Año de acta, Ubicación registral, contacto directo en Titular/Solicitante — ninguno existe en V2) en vez de portar la estructura real de `JPanelRegistroManualRecepcionV2.java`.
2. La primera versión de "Bandeja Registro" omitió columnas reales de V2 (`Canal`, `Tipo Acta`, `Nro Acta`) y no respetó el orden exacto de `crearTableModel(...)`.

**Cómo aplicar**: antes de escribir cualquier página/formulario/bandeja nueva, grep + Read del `JPanelXxxV2.java` correspondiente (columnas de `DefaultTableModel`, bloques de `AppV2SideSectionPanel`, orden de campos). No inventar agrupamiento aunque parezca más prolijo — si hay que mejorar la UX (ej. ocultar columnas por defecto con "Manage columns"), eso es libertad de diseño; omitir o reordenar datos reales no lo es.

## Stack

- **Backend**: `v3/sdrerc-v3-backend` — Spring Boot 3.5.16, **Java 17** (separado del Java 8 de V2), Maven con `pom.xml` propio, **no** es `<module>` del `pom.xml` raíz (para no afectar el build de V2). Paquete base `com.sdrerc.v3.*`.
- **Frontend**: `v3/sdrerc-v3-frontend` — React 19 + TypeScript + Vite + MUI (incluye MUI X Data Grid v9.11.0), Recharts para gráficos, `qrcode.react` para el QR de enrolamiento TOTP.
- **BD**: la misma Oracle `SDRERC_APP` compartida con V2. Acceso vía `DataSource` gestionado por Spring Boot (HikariCP), no el `SdrercAppConnection` estático de V2.
- **Auth**: JWT stateless (`io.jsonwebtoken`/jjwt 0.13.0). Reemplaza el singleton `SessionContext` de V2 por `CurrentUser` (request-scoped, resuelto desde `SecurityContextHolder`).

## Patrones de arquitectura ya establecidos

Aplican a todo módulo nuevo que se porte, no son decisiones puntuales de un módulo:

- **Identidad de sesión**: `CurrentUser.get()` (`security.jwt`) es el único punto del backend que toca `SecurityContextHolder` directamente. Services/DAOs reciben `idUsuario`/roles como parámetro explícito — es la generalización del patrón `VisibilidadBandejaSql` que ya existía en V2. Nunca reintroducir una consulta "usuario actual por username" como hacía V2 (`UsuarioAsignacionService.resolverUsuarioActualSdrercApp()`): el JWT ya trae el `idUsuario` directo.
- **Conexión a BD**: DAOs reciben `DataSource` por constructor (`@Repository`), abren `Connection` con try-with-resources por operación. Nunca un holder estático.
- **DTOs**: se portan casi literal desde V2, como **clases con getters** (no records) cuando el DTO original tiene lógica derivada reutilizable (`isAsignable()`, `getAlertaIngreso()`, etc.) — Jackson serializa esos métodos igual que los campos, y el frontend reutiliza esa lógica de negocio en vez de reimplementarla en TypeScript. DTOs simples de catálogo (`CatalogoItemDTO`, `UbigeoItemDTO`) sí usan `record`.
- **DAOs grandes de V2 se portan acotados**, no completos: solo los métodos que el incremento actual necesita, documentado explícitamente en el Javadoc de la clase (qué se omitió y por qué). Ver `AsignacionExpedienteDAO` como ejemplo de referencia de este patrón.
- **Compatibilidad retro de V2 se omite**: los chequeos `soportaNumeroHojaEnvio(conn)`/`soportaGrupoFamiliar(conn)`/etc. (feature-detection contra columnas que podían no existir en versiones viejas del esquema) no se portan — la BD compartida por V3 ya tiene todas esas columnas, se asumen presentes siempre.
- **Excepciones de negocio**: validaciones tipo "El equipo destino no está activo" se lanzan como `IllegalArgumentException`/`IllegalStateException` (unchecked), no como `SQLException`. `GlobalExceptionHandler` traduce esas dos a HTTP 400 con el mensaje real; `SQLException` genérico queda reservado para fallas reales de conexión/BD y se resume a un mensaje 500 genérico (no expone detalle interno). Si un DAO nuevo porta una validación de V2 que originalmente lanzaba `SQLException` con mensaje para el usuario, cambiarla a `IllegalStateException` en el port.
- **Autor de historial cuando actúa ADMIN_SISTEMA** (regla de negocio de V2, ver `CLAUDE.md` raíz): en V3 se resuelve con `CurrentUser.get().hasRole("ADMIN_SISTEMA")` (ya viene en el JWT), no con la query `CatalogoLookupDAO.tieneRolAdminSistema` que usa V2.
- **Scoping por incremento**: cada fase se corta en el primer slice funcionalmente completo y verificable (no el módulo completo de V2 de una sola vez). Lo que queda fuera se documenta explícitamente en el Javadoc del controller/DAO del incremento, para que el siguiente incremento sepa exactamente qué falta.

## Patrones de frontend (páginas de bandeja)

- Buscador de 3 filas: texto+Buscar/Limpiar, fechas desde/hasta, combos+límite — mismo patrón visual en toda bandeja nueva (`RegistroBandejaPage.tsx`/`AsignacionBandejaPage.tsx` como referencia).
- KPIs calculados **en memoria** sobre la lista ya cargada (mismo patrón que V2: `actualizarMetricasXxx`/`filtrarPorXxx` en el `JPanelXxxV2.java`), nunca una query de conteo aparte.
- `DataGrid` (MUI X v9) con columnas en el **mismo orden exacto** que la tabla Swing real (`crearTableModel`/`XxxTableModel` en V2).
- `GridRowSelectionModel` en MUI X v9 es `{ type: 'include' | 'exclude', ids: Set<GridRowId> }`, no un array plano — cambió de forma entre versiones de MUI X, ojo si se copia código de ejemplos viejos.
- Llamadas API con **rutas relativas** (`/api/...`, ver `src/api/http.ts`): funcionan igual en local y en acceso remoto por Tailscale porque Vite proxea `/api` del lado del servidor (`vite.config.ts`), el navegador nunca necesita saber el host/puerto real del backend.

## Vistas Oracle para SELECT de bandejas (regla permanente, pedido explícito del usuario, 12/08/2026)

Cuando un DAO de listado (bandeja) necesita un SELECT con varios joins/subconsultas (no un CRUD simple), el SQL de lectura se formaliza como `CREATE OR REPLACE VIEW` en un script nuevo de `db/sdrerc_app/scripts` (numeración correlativa, mismo patrón que los scripts de V2), y el DAO consulta la vista por nombre (`SELECT * FROM vw_xxx WHERE <filtros dinámicos>`) en vez de repetir el join completo como texto en Java. Precedente ya existente en V2: `vw_expediente_bandeja` (script `10_vistas_bandejas_consola.sql`), ya usado por `ExpedienteBandejaDAO` (Bandeja Registro). Primer caso aplicado en V3: `vw_expediente_asignacion_detalle` (script `99_vista_expediente_asignacion_detalle.sql`), usado por `AsignacionExpedienteDAO.buscarExpedientes`.

Reglas de cómo aplicar esto:

- **Solo el lado de lectura** (SELECT de listados/bandejas). Los INSERT/UPDATE/DELETE de acciones (asignar, registrar, reasignar, etc.) siguen en Java con `PreparedStatement` — **no** se mueven a procedimientos almacenados. Esto ya estaba decidido explícitamente en `PLAN_MIGRACION_SDRERC_V3.md` (sección 6, nota de procedimientos): partiría la lógica de negocio entre Java y PL/SQL nueva, con más riesgo de romper reglas sensibles (visibilidad por asignación, permisos, sustitución de autor ADMIN_SISTEMA) que beneficio real.
- Los filtros **dinámicos** por request (texto libre, estado, fechas, límite) NO van dentro de la vista — se siguen aplicando en el DAO como `WHERE` sobre `SELECT * FROM vista`. Solo lo que es **constante** (reglas de negocio fijas, ej. "no mostrar duplicados asociados como fila principal") va dentro de la vista.
- Si el DAO original tenía constantes pasadas como bind param en Java (ej. códigos de catálogo fijos), en la vista van literales — una vista no acepta parámetros.
- Antes de crear una vista nueva, revisar si `vw_expediente_bandeja` (genérica, columnas básicas compartidas por todas las bandejas) ya alcanza; si el listado necesita columnas propias que no tiene sentido agregar a una vista compartida por otros módulos, se crea una vista nueva y específica (no se infla la genérica).
- **Cada script de vista nueva se crea pero NO se ejecuta automáticamente** — sigue la misma regla de siempre ("no ejecutar SQL sin autorización explícita"). Hasta que el usuario lo corra manualmente contra Oracle, el DAO que la consulta **no funciona** (rompe con "vista no existe"); no reiniciar/desplegar esa versión del backend antes de confirmar que el script ya se ejecutó. Ver lista de scripts pendientes abajo.
- V2 (escritorio) nunca se modifica ni depende de estas vistas nuevas — son aditivas, de solo lectura, pensadas únicamente para que las consuma V3.

## Entorno de desarrollo

- **Arranque rápido**: `powershell -ExecutionPolicy Bypass -File v3\start-dev.ps1` (lee las variables de entorno de usuario ya configuradas + SMTP de `config/sdrerc-app.properties`, levanta backend+frontend, healthcheck).
- **JDK 17**: `C:\Program Files\Eclipse Adoptium\jdk-17.0.20.8-hotspot` (Temurin, instalado vía winget, conviviendo con el JDK 8 de V2 sin tocar `JAVA_HOME` global).
- **Variables de entorno de usuario** (persisten tras reiniciar): `SDRERC_V3_DB_URL`, `SDRERC_V3_DB_USER`, `SDRERC_V3_DB_PASSWORD`, `SDRERC_V3_JWT_SECRET`. Las variables SMTP (`SDRERC_APP_SMTP_*`) **no** se persisten como env vars de usuario: se leen en caliente de `config/sdrerc-app.properties` en cada arranque (nunca se imprimen/loguean).
- **Truststore TLS local** (para SMTP con interceptor TLS local, ej. Norton): copia en `%USERPROFILE%\.sdrerc-v3-trust\cacerts`, importado desde `scripts/client/smtp-root-cert.cer` (asset ya existente de V2). El backend se lanza con `-Djavax.net.ssl.trustStore=...` y `-Djavax.net.ssl.trustStorePassword=changeit`.
- **Rebuild backend** tras cambios Java:
  ```powershell
  Get-CimInstance Win32_Process -Filter "Name='java.exe'" | Where-Object { $_.CommandLine -like '*sdrerc-v3-backend.jar*' } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
  $env:JAVA_HOME = "C:\Program Files\Eclipse Adoptium\jdk-17.0.20.8-hotspot"
  $env:MAVEN_OPTS = "-Djavax.net.ssl.trustStore=$env:USERPROFILE\.sdrerc-v3-trust\cacerts -Djavax.net.ssl.trustStorePassword=changeit"
  mvn -f v3\sdrerc-v3-backend\pom.xml clean package -DskipTests -q
  ```
  Hay que detener el `java.exe` que corre el jar antes de `clean` (si no, Maven falla con "el proceso no tiene acceso al archivo").
- **Type-check frontend**: `npx tsc --noEmit` dentro de `v3/sdrerc-v3-frontend`.
- **Reinicio del frontend** (necesario tras tocar `vite.config.ts`, no tras tocar `index.html` — eso Vite lo recarga solo):
  ```powershell
  Get-CimInstance Win32_Process -Filter "Name='node.exe'" | Where-Object { $_.CommandLine -match 'vite' } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
  Start-Process -FilePath "npm.cmd" -ArgumentList "run","dev" -WorkingDirectory "v3\sdrerc-v3-frontend" -WindowStyle Hidden
  ```

### Acceso remoto (laptop cliente) vía Tailscale

Configurado el 2026-08-12 para que la laptop cliente (la misma que ya usa V2 y su VPN Tailscale para llegar a Oracle) también pueda abrir V3 en modo desarrollo, sin tocar su configuración de VPN/V2 en absoluto (Tailscale es mesh: cada dispositivo es independiente, agregar/exponer algo en esta máquina no modifica la del cliente).

- `vite.config.ts`: `server.host = true` (escucha en todas las interfaces, no solo `localhost`). El backend (puerto 8081) **no** necesita exponerse: Vite lo proxea internamente desde el propio proceso.
- Regla de firewall de Windows (requiere PowerShell como Administrador, esta sesión no tiene privilegios elevados):
  ```powershell
  New-NetFirewallRule -DisplayName "SDRERC V3 dev (Vite 5173)" -Direction Inbound -Protocol TCP -LocalPort 5173 -Action Allow -Profile Private
  ```
- Acceso desde la laptop cliente: `http://<IP-Tailscale-de-esta-máquina>:5173` (verificar con `tailscale status` en esta máquina).
- Esto es exclusivo de **desarrollo**. El plan de migración (sección 2) ya define que producción sirve el build estático del frontend junto al backend en el mismo origen — ahí no hace falta nada de esto.
- **Gotcha real ya resuelto**: `index.html` tenía `lang="en"` en una app 100% en español. Eso hacía que el navegador (probado desde la laptop cliente) ofreciera traducir la página; el traductor automático modifica el DOM por fuera de React y provoca `Uncaught NotFoundError: Failed to execute 'removeChild'` al re-renderizar (ej. justo después del login), dejando la pantalla en blanco. Fix: `<html lang="es" translate="no">` + `<meta name="google" content="notranslate">`. No es un bug de red/Tailscale — puede repetirse en cualquier acceso nuevo si se revierte ese `index.html`.

### Fase 2 — Registro — módulo completo (Registro Manual + Bandeja Registro + Carga diaria + Edición manual + expansión de filas + Panel de datos)
- Registro Manual (`/api/registro/manual/validar`, `/api/registro/manual`): alta con detección de duplicado por acta+titular/N° SGD y posible grupo familiar. Verificado con una solicitud real, cruzada en la Bandeja Registro de V2.
- Bandeja Registro (`/api/registro/bandeja`): listado + filtros + 3 KPIs (Potencial duplicado, Posible Grupo Familiar, Grupo Familiar Confirmado), columnas idénticas a `crearTableModel(perfilRegistroRecepcion=true)` de V2, con "Manage columns" para Canal/Tipo Acta/Nro Acta (ocultas por defecto, no persistido). Botón "Carga diaria" agregado junto a "+ Registro manual".
- Carga diaria (construido, módulo completo — **sin verificar en navegador todavía**): subir Excel/CSV → parsear → validar (mismas reglas que Registro manual: duplicados por acta+titular en archivo y en base, N° SGD único, posible grupo familiar, número preliminar) → previsualización EDITABLE → botón "Validar" tras editar → Confirmar y registrar → exportar previsualización a Excel → descargar plantilla oficial. Los 3 items originalmente diferidos (edición de celdas, exportar a Excel, descarga de plantilla) ya se construyeron en un incremento posterior, a pedido explícito del usuario ("avanza con edición de celdas en la previsualización, exportar a Excel, descarga de plantilla"). Página `/registro/carga-diaria` (`RegistroCargaDiariaPage.tsx`), grilla de 20 columnas igual a `JPanelCargaDiariaRecepcionV2.tableModel` de V2 (mismo orden/encabezados).
  - Backend: `RegistroCargaDiariaController` — `POST /previsualizar` (multipart), `POST /validar` (JSON, re-ejecuta reglas sobre una lista editada), `POST /confirmar` (JSON), `POST /exportar` (JSON → `.xlsx` binario), `GET /plantilla` (`.xlsx` binario) — más `CargaDiariaExpedienteService` (orquesta las 5 acciones). A diferencia de V2 (que separa "Previsualizar" del texto crudo y "Validar" con reglas de negocio porque el usuario puede editar celdas entre medio), V3 combina parseo+validación en la única llamada `previsualizar` inicial (no hay edición todavía en ese punto) y reserva el endpoint `/validar` exclusivamente para revalidar tras editar — mismo resultado final, un paso de red menos en el caso más común (subir y confirmar sin editar).
  - `CargaDiariaArchivoParserService` portado casi literal (mismo motor de detección de encabezados por alias, Apache POI `poi-ooxml` agregado como dependencia nueva del backend V3, misma versión 5.2.5 que V2); único cambio real es que recibe `InputStream`+nombre de archivo (de un multipart HTTP) en vez de `java.io.File` (V2 usaba `JFileChooser`).
  - `CargaDiariaReglasService` portado literal, sin cambios de comportamiento.
  - `CargaDiariaPlantillaService` portado casi literal (misma plantilla: hoja CARGA_DIARIA con listas desplegables + validaciones de documento de identidad por fórmula, hoja CATALOGOS oculta, hoja INSTRUCCIONES); único cambio real es que `generarPlantilla()` devuelve `byte[]` (para servir por HTTP) en vez de escribir a un `File` elegido con `JFileChooser`.
  - `CargaDiariaExportService` (nuevo, sin equivalente de clase propia en V2 — la lógica vivía inline en `JPanelCargaDiariaRecepcionV2.escribirExcelPrevisualizacion`/`numeroExpedientePreview`/`observacionValidacionTabla`, movida a un Service porque V3 no tiene un `JTable` del que leer valores ya formateados): reconstruye las mismas 20 columnas con el mismo formato que mostraba el `JTable` de V2 (fecha dd/MM/yyyy, documento "SIN DNI" vacío, canal con nombre visible, duplicidad Sí/No, número de expediente con los mismos 3 textos de respaldo "Pendiente"/"Sin número por duplicado"/"Sin número por procedimiento", observación consolidada en frases "Dato incompleto: X").
  - `ExpedienteRegistroDAO` (V3) extendido con el camino de Carga diaria: `detectarDuplicadosContraBase`, `detectarDuplicadosPorNumeroSgdContraBase`, `detectarPosiblesGruposFamiliaresContraBase`, `detectarDuplicadosPorTitularExactoContraBase`, `obtenerSiguienteCorrelativoExpediente`, `registrarCarga(registros, idUsuarioActual)` (mismo patrón que `registrarManual`: `idUsuarioActual` explícito en vez de `SessionContext` estático). Los métodos de inserción específicos de Carga diaria se nombraron con sufijo `*Carga` (`insertarExpedienteCarga`, `insertarSolicitudCarga`, etc.) para no chocar con los `*Manual` ya existentes — en V2 no hay colisión de nombres porque Carga diaria y Registro manual son DAOs separados en la práctica de uso aunque compartan clase.
  - `CatalogoLookupDAO` (V3) ganó `obtenerTipoActaIdPorCodigoONombre` (Carga diaria trae "Tipo de acta" como texto libre de la plantilla, puede venir como código o nombre, a diferencia de `obtenerTipoActaId` que exige código exacto).
  - `GlobalExceptionHandler` ganó un handler de `IOException` → 400 (antes solo `IllegalArgumentException`/`IllegalStateException`/`SQLException`/`InvalidTokenException`); el parser lanza `IOException` cuando el archivo no se puede leer (dañado, formato no soportado, columnas obligatorias faltantes).
  - `application.yml` ganó `spring.servlet.multipart.max-file-size`/`max-request-size` en 20MB (no configurado antes porque no había endpoints de subida de archivos en V3).
  - Frontend: columnas de datos importados (las 16 primeras) editables inline en el `DataGrid` (`editable`/`isCellEditable`, deshabilitado si `registrado=true`, igual criterio que `esCeldaEditable` de V2); botón "Validar" nuevo que reenvía la lista completa (editada) a `/validar`. **Diferencia deliberada de comportamiento respecto a V2 (no de datos, ver Javadoc de la página)**: V2 permite confirmar sin volver a validar tras una edición porque `actualizarValidacionLocal` no toca `listoParaRegistrar`; V3 marca la fila `Pendiente` y limpia `listoParaRegistrar` en cada edición (`processRowUpdate`), obligando a presionar "Validar" antes de habilitar "Confirmar carga" — mismo resultado una vez validada, pero cierra la ventana de confirmar con duplicados/número desactualizados. Columnas "Duplicidad"/"Número expediente"/"Observación" replican en TypeScript la misma lógica de formato que `CargaDiariaExportService` (backend) para que grilla y Excel exportado se vean iguales — helpers `numeroExpedientePreview`/`observacionValidacionTabla`/`convertirADatoIncompleto` en `RegistroCargaDiariaPage.tsx`. Botones "Exportar" y "Descargar plantilla" usan nuevos helpers `apiPostBlob`/`apiGetBlob`/`descargarBlob` en `api/http.ts` (primera vez que V3 descarga binarios autenticados, no solo JSON).
- Edición manual (construido — **sin verificar en navegador todavía**), a pedido explícito del usuario tras confirmar Carga diaria completa. Botón "Editar" por fila en la Bandeja Registro (`RegistroBandejaPage.tsx`), habilitado solo si `etapaCodigo==='REGISTRO' && estadoCodigo==='REGISTRADO' && !responsableActual` (mismo criterio superficial que V2, `esRegistroSeleccionadoEditable`; el backend vuelve a validar con lock pesimista, es la fuente de verdad real) → navega a `/registro/editar/:idExpediente` (`RegistroEdicionManualPage.tsx`). - Frontend: página nueva `AsignacionCartasRespuestaPage.tsx` (ruta `/asignacion/cartas-respuesta`, botón "Cartas de respuesta" en `AsignacionBandejaPage.tsx`) — página separada, no pestaña dentro de la misma página, mismo criterio que ya se usa para Registro/Asignación como rutas independientes. 11 columnas exactas y mismo orden que `bandejaCartasRespuestaModel` en V2 (Días, Fecha Vencimiento, N° expediente, N° expediente SGD, Titular, Tipo documento, N° Documento, Fecha Acuse, Fecha Publ. Notif., Fecha Publ. Edicto, Estado) + 5 KPIs (Cartas, Con acuse, Pendientes, Publicación, Vencimiento) + filtro por texto/fecha vencimiento/estado, todo en memoria sobre la lista completa (mismo patrón que V2: "todo el filtrado sigue siendo en memoria").
- Columna "Estado" (`getEstadoCarta()` en el DTO): "Edicto Publicado" si ya hay `fechaPublicacionEdicto`, "Pendiente de Respuesta" en cualquier otro caso — mismo criterio que `estadoCartaRespuesta()` en V2.
- Vencimiento en cascada portado literal: mientras no haya Fecha Publ. Edicto, el plazo corre desde Fecha Acuse (o Fecha Publ. Notif. si no hay acuse directo); en cuanto se registra Fecha Publ. Edicto, el plazo cambia a "publicación" desde esa fecha. Usa `PlazoConfiguracionDAO.obtenerPlazoPorCodigo` (código del tipo de documento, o ese código + `_PUBLICACION`) y `CalendarioLaboralService.calcularFechaVencimientoHabil`/`calcularDiasHabilesRestantes`, ambos ya existentes en V3.
- **Diferido explícitamente — es la pieza más grande que falta de este módulo**: el botón "Registrar Asignación" (deriva el expediente de vuelta a Análisis con estado `ANALISIS/DERIVADO` vía `AsignacionExpedienteDAO.reasignarDesdeCartaRespuesta`, y exige que la carta intermedia ya tenga una carta de respuesta agregada como documento hijo en la grilla). No se portó porque depende de gestión jerárquica de documentos analizados (padre/hijo, `EXPEDIENTE_DOCUMENTO_ANALIZADO`), que es territorio de Análisis (Fase 4) y no existe en V3 todavía — construirlo ahora habría significado adelantar buena parte de Análisis fuera de orden. Por eso esta bandeja es hoy un tablero de seguimiento, no un flujo de trabajo completo.

### Carga Abogados — sub-pestaña de Asignación (construido, solo lectura, sin verificar en navegador)

`CargaLaboralAbogadoDAO`/`CargaLaboralAbogadoDTO` ya existían desde la Fase 1 (los usa el gráfico "Carga por abogado" del Dashboard); este incremento los extiende con lo que le faltaba al DAO (`listarDocumentosPorAbogado`, `listarIdsUsuarioConVencimientoEnRango`) para armar la bandeja completa, sin tocar el uso que ya hace `DashboardService`.

- Backend: `CargaLaboralAbogadoDAO` extendido + `CargaLaboralAbogadoService` (nuevo) + 3 endpoints en `AsignacionController` (`GET /api/asignacion/carga-abogados?idEquipo=`, `GET /api/asignacion/carga-abogados/{idUsuario}/documentos`, `GET /api/asignacion/carga-abogados/vencimiento?desde=&hasta=`).
- Frontend: página nueva `AsignacionCargaAbogadosPage.tsx` (ruta `/asignacion/carga-abogados`, botón "Carga Abogados" en `AsignacionBandejaPage.tsx`). Grilla: Abogado + 4 subcolumnas de la carga de Análisis (Por recibir, En análisis, Observado, Carta intermedia) — mismas 5 columnas y mismo orden que `cargaLaboralModel` en V2. Supervisor/Por vencer/Vencidos **no son columnas** de la grilla (mismo criterio que V2): Supervisor es un combo del buscador, Por vencer/Vencidos son KPIs clicables que filtran por `porVencer > 0`/`vencidos > 0`.
- 6 KPIs con la misma fórmula exacta que `actualizarMetricasCargaLaboral` en V2: Abogados (cantidad de filas), Con carga/Sin carga (según `enAnalisis() > 0`, no según carga total), Solicitudes/Por vencer/Vencidos (**sumas** de `cargaTotal()`/`porVencer`/`vencidos` sobre todas las filas, no conteos).
- Filtro de fecha (Fecha vencimiento desde/hasta): resuelve primero el `Set` de ids de abogado con expediente vencido en el rango (`GET /api/asignacion/carga-abogados/vencimiento`) y luego intersecta en memoria — mismo patrón de 2 pasos que `aplicarFiltrosCarga`/`aplicarFiltrosCargaConIds` en V2. Resto de filtros (texto, combo Abogado, combo Supervisor, límite — default 100) en memoria directo sobre la carga ya cargada, sin rango de fecha por defecto (a diferencia de otras bandejas, que sí traen un mes por defecto).
- Panel "Detalle de carga" (doble clic sobre una fila): diálogo con N° Expediente/Etapa/Estado/Días — **exclusivamente** la carga de Análisis del abogado (mismo alcance que `listarDocumentosPorAbogado`: `ASIGNACION/ASIGNADO` o cualquier estado de `ANALISIS`), no incluye Verificación ni Ejecución, igual que V2.
